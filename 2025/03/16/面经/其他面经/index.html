长轮询、短轮询、WebSocket

由于HTTP协议是请求-响应模式，请求必须在前，响应必须在后，这就导致了服务器无法【主动】的把消息告诉客户端。解决方案就是webSocket。

短轮询：

每隔一段时间客户端就会向服务端发送请求，客户端只需要设置一个定时器不断发送请求即可。（话痨式）

缺陷：

  • 会产生大量无意义的请求
  • 会频繁打开关闭连接
  • 实时性并不高

长轮询：

客户端一开始就发送请求到服务器，服务器响应之后返回给客户端，客户端立即发起下一个请求。请求和响应的次数减少了很多，都是有意义的。

缺陷：

  • 客户端长时间收不到响应会导致超时，从而主动断开和服务器的连接

    这种情况是可以处理的，但ajax请求因为超时而结束时，立即重新发送请求到服务器，最然这种做法会让之前的请求变得毫无意义，但毕竟比短轮询好多了

  • 由于客户端可能【过早的】请求了服务器，服务器不得不挂起这个请求直到新消息的出现。这会让服务器长时间的占用资源却没什么实际的事情可做。

WebSocket：

从上图可以看出：

  • WebSocket也是建立在TCP协议之上的，利用的是TCP全双工通信的能力
  • 使用WebSocket，会经历两个阶段：握手阶段、通信阶段

缺陷：

  • 兼容性

    WebSocket是HTML5新增的内容，因此古董版本的浏览器并不支持

  • 维持TCP连接需要耗费资源

    对于那些消息量少的场景，维持TCP连接确实会造成资源的浪费

    为了充分利用TCP连接的资源，在使用了WebSocket的页面，可以放弃使用ajax，都用WebSocket进行通信，当然这会带来程序设计上的一些问题，需要权衡。

参考回答:
当组件创建和更新时，vue均会执行内部的update函数，该函数使用render函数生成的虚拟dom树，将新旧两树进行对比，找到差异点，最终更新到真实dom

对比差异的过程叫diff，vue在内部通过一个叫patch的函数完成该过程

在对比时，vue采用深度优先、同层比较的方式进行比对。

在判断两个节点是否相同时，vue是通过虚拟节点的key和tag来进行判断的

具体来说，首先对根节点进行对比，如果相同则将旧节点关联的真实dom的引用挂到新节点上，然后根据需要更新属性到真实dom，然后再对比其子节点数组；如果不相同，则按照新节点的信息递归创建所有真实dom，同时挂到对应虚拟节点上，然后移除掉旧的dom。

在对比其子节点数组时，vue对每个子节点数组使用了两个指针，分别指向头尾，然后不断向中间靠拢来进行对比，这样做的目的是尽量复用真实dom，尽量少的销毁和创建真实dom。如果发现相同，则进入和根节点一样的对比流程，如果发现不同，则移动真实dom到合适的位置。

这样一直递归的遍历下去，直到整棵树完成对比。

diff算法就是当数据更新时，比较新dom树和旧dom树，对两棵树进行对比更新。

2. _update 函数再干什么

_update 函数接收到一个vnode参数，这就是新生成的虚拟dom树

同时，_update函数通过当前组件的_vnode属性，拿到旧的虚拟dom树

_update函数首先会给组件的_vode属性重新赋值，让它指向新树

然后判断旧树是否存在：

  • 不存在：说明这是第一次加载组件，于是通过内部的patch函数，直接遍历新树，为每个节点生成真实DOM，挂载到每个节点的elm属性上

  • 存在：说明之前已经渲染过该组件，于是通过内部的patch函数，对新旧两棵树进行对比，以达到下面两个目标：

    • 完成对所有真实dom的最小化处理
    • 让新树的节点对应合适的真实dom

3. patch函数的对比流程

术语解释：

  1. 相同：是指两个节点的标签类型、key值均相同，但input元素还要看type属性
  2. 新建元素：是指根据一个虚拟节点提供的信息，创建一个真实dom元素，同时挂载到虚拟节点的elm属性上
  3. 销毁元素：是指：vnode.elm.remove()
  4. 更新：是指对两个虚拟节点进行对比更新，它仅发生再两个虚拟节点相同的情况下。具体过程稍后描述
  5. 对比子节点：是指对两个虚拟节点的子节点进行对比，具体过程稍后描述

详细流程：

  1. 根节点比较

    patch函数首先对根节点进行比较

    如果两个节点：

    • 相同，进入更新流程
      1. 将旧节点的真实dom赋值到新节点：newVnode.elm = oldVnode.elm
      2. 对比新节点和旧节点的属性，有变化的更新到真实dom中
      3. 当前两个节点处理完毕，开始对比子节点（深度优先）
    • 不相同
      1. 新节点递归新建元素
      2. 旧节点销毁元素

  2. 对比子节点

    在对比子节点时，vue一切的出发点，都是为了：

    • 尽量啥也别改
    • 不行的话，尽量仅改动元素属性
    • 还不行的话，尽量移动元素，而不是删除和创建元素
    • 还不行的话，删除和创建元素

ps：尽量不动元素，新旧dom树都创建两个头尾指针进行对比，把一样的dom元素移动，剩下的不一样的元素再进行删除或创建

XHR，AJAX，Fetch，Axios的区别

XHR

XMLHttpRequest （XHR）是一个 JavaScript 对象，它可以用来向服务器发送 HTTP 请求，从而实现网页的局部更新。是 AJAX 编程的核心技术。

AJAX

AJAX 代表异步的 JavaScript 和 XML（Asynchronous JavaScript And XML）。简单点说，就是使用 XMLHttpRequest（XHR）对象与服务器通信。

Ajax 本身不是一种编程语言，而是一种利用以下技术的组合。

  • 浏览器内置的XMLHttpRequest对象（向服务器请求数据）
  • JavaScript和HTML DOM（显示或使用数据）
  • XML、JSON或纯文本（作为数据传输格式）

Ajax 中的 X 代表 XML，但是 JSON 才是首选，因为它更加轻量

XML（可扩展标记语言）是一种基于文本的标记语言，设计核心目标为结构化数据的传输与存储，其通过自定义标签实现跨平台、跨程序的数据描述。作为 W3C 推荐标准，XML 具备以下特性：

核心特性

  1. 可扩展性
    与 HTML 固定标签集不同，XML 允许用户根据需求自定义标签（如<note>、<order>），标签名称需符合字母开头、避免空格等命名规则。
  2. 结构化数据表达
    采用树形层级结构组织数据，要求文档必须包含唯一的根元素（如<catalog>），子元素通过嵌套形成清晰的数据关系，适用于表示复杂数据模型。
  3. 平台与语言独立性
    数据以纯文本形式存储，天然支持异构系统间的数据交换，广泛应用于 Web 服务（SOAP）、配置文件（Spring/Android）、企业数据集成等场景。

语法规范

  • 严格格式约束
    所有标签必须闭合，属性值需引号包裹，元素大小写敏感，嵌套顺序不可错乱。例如：

  • 元数据声明
    文档首行需声明版本与编码（如<?xml version="1.0" encoding="UTF-8"?>），确保解析器正确处理内容。

  • 特殊字符处理
    使用实体引用（如<代表<）或 CDATA 区块包裹原始文本，避免符号被误解析。

个人理解：与html相比，虽然都是标签来表达，但是xml用于存储与传输数据，html用于可视化页面；与json相比，都是存储与传输数据的格式，但是xml是标签包裹数据，json是键值对形式。

AJAX的工作原理

  • 在网页中发生一个事件（页面加载，按钮被点击等）
  • JavaScript创建一个XMLHttpRequest对象
  • XMLHttpRequest对象向服务器发送一个请求
  • 服务器处理请求
  • 服务器向网页返回一个响应
  • JavaScript读取响应
  • JavaScript执行相应的操作（如更新网页）

Ajax的优缺点

优点：

  1. 减少页面刷新：Ajax 可以在页面不刷新的情况下获取和显示数据，减少了用户等待时间和流量消耗。
  2. 提高用户体验：由于 Ajax 可以实现异步请求和响应，使得用户可以在不中断操作的情况下获取数据，从而提高了用户的体验。
  3. 减轻服务器压力：由于 Ajax 可以部分更新页面，减少了服务器处理请求的次数，从而减轻了服务器的压力。
  4. 支持多种数据格式：Ajax 可以支持多种数据格式，如 XML、JSON 等，使得数据的传输和处理更加灵活。

缺点：

  1. 对 SEO 不友好：由于 Ajax 的异步请求不会刷新整个页面，搜索引擎很难获取 Ajax 加载的数据，从而降低了网站的 SEO 优化效果。
  2. 安全性问题：Ajax 可能会导致跨站点脚本攻击（Cross-site scripting, XSS）和跨站点请求伪造（Cross-site request forgery, CSRF）等安全问题，开发人员需要采取相应的安全措施。

Fetch

Fetch 是 XMLHttpRequest 的升级版，用于在 JavaScript 脚本里面发出 HTTP 请求。是基于promise的。

优点

  • 支持跨域请求：在配置中，添加mode： ‘no-cors’就可以跨域了
  • 可以自定义请求头，更好地控制请求。

缺点

  • fetch只对网络请求报错，对400，500都当做成功的请求，需要封装去处理
  • fetch没有办法原生监测请求的进度，而XHR可以。

Axios

Axios是一个基于promise网络请求库，在服务端它使用原生 node.js http 模块, 而在客户端 (浏览端) 则使用 XMLHttpRequests。

Axios的优缺点

优点：

  1. Promise API：Axios使用Promise API，因此可以轻松处理异步操作。Promise API具有更清晰的语法和更好的可读性，因为它们允许在异步操作完成之前进行链式调用，从而避免了回调地狱问题。
  2. 简单易用：Axios的API设计简单且易于使用，而且它还提供了许多可用的配置选项，例如设置请求头、超时时间、认证等等，让开发者可以更轻松地定制请求。
  3. 可扩展性：Axios可以通过添加拦截器(interceptors)来实现许多自定义功能，例如添加请求拦截器、响应拦截器和错误拦截器等等。这些拦截器可以让开发者在请求和响应过程中进行自定义操作。

缺点：

  1. 可能出现跨域问题：Axios不能直接解决跨域请求的问题。尽管Axios可以设置跨域请求头，但是它不能绕过浏览器的安全限制。这意味着在某些情况下，开发者可能需要通过其他方式来解决跨域请求的问题。

总结

XHR：是一个 JavaScript 对象

ajax：是一个技术统称，XMLHttpRequest 是实现 Ajax 的一种方式。

fetch：是一个API，es6新增的用于网络请求标准api。

axios：是一个库，用于网络请求的第三方库。

CORS（跨源资源共享）头是服务器在 HTTP 响应中设置的一组特定字段，用于授权浏览器执行跨域请求，突破同源策略的安全限制。其核心作用在于定义哪些外部域、HTTP 方法及请求头可被允许访问当前服务器的资源。

会话

会话始于客户端首次向服务器发起请求，终止于任意一方断开连接（如关闭浏览器或会话超时）。其存在解决了 HTTP 协议无状态的局限性，使得用户登录凭证、购物车信息等数据能够在多次交互中持续传递。

默认超时时间由服务器配置（如 Tomcat 默认 30 分钟），用户活动可重置超时计时。若采用无状态会话（如 Token 机制），则每次请求独立，无固定周期。

关键影响因素

  • 超时配置：服务端设置的会话空闲超时时间。
  • 显式操作：主动调用会话关闭接口（如sess.close()或session.invalidate()）。
  • 网络状态：连接中断可能导致临时会话终止，而持久会话可恢复。
  • 用户行为：Web 会话通过持续交互延长周期，系统会话随用户登录状态变化。

怎么防御XSS和CSRF

跨站脚本攻击（XSS）

定义: XSS（Cross-Site Scripting）是一种攻击方式，攻击者将恶意脚本注入到网页中，当其他用户访问该页面时，恶意脚本会在其浏览器中执行，从而窃取用户信息或执行其他恶意操作。

防护措施:

  • 输出编码: 对用户输入进行正确的编码，确保在插入到 HTML、JavaScript、CSS 等内容中时不会被解释为脚本。可以使用函数如 encodeURIComponent()、escape()、htmlspecialchars() 等。

  • 输入验证: 验证和过滤用户输入，确保数据符合预期格式，避免恶意代码注入。

  • 使用Content Security Policy (CSP):

    CSP 是一种安全机制，通过设置Content-Security-Policy头，限制网页可以加载的资源和脚本来源，从而减少 XSS 攻击的风险。

  • 避免 eval 和动态代码执行: 避免使用 eval()、setTimeout() 和 setInterval() 等可能执行动态代码的功能。

跨站请求伪造（CSRF）

定义: CSRF（Cross-Site Request Forgery）是一种攻击方式，攻击者诱使用户在已认证的网页上执行不希望的操作，例如提交表单或发起请求，从而劫持用户的会话。

防护措施:

  • 使用 CSRF 令牌: 在每个敏感操作中，要求附带 CSRF 令牌。令牌应随机生成且与用户会话关联，防止被伪造。

  • 验证 HTTP Referer 头: 检查请求的 Referer 头，以确保请求来自受信任的来源。

  • 使用 SameSite Cookie 属性: 将 Cookie 的 SameSite 属性设置为Strict或Lax，防止第三方站点发起的跨站请求带上 Cookie。

http和tcp的长链接的区别

Keep-alive

http和tcp他们都有，但是有区别

http层面（应用层）

发起请求需要进行tcp三次握手，请求结束后断开，再次发起请求需要再次三次握手，很浪费网络性能。

所以开启keep-alive之后，可以下次请求的时候，复用上次的tcp链接，提升传输性能。

tcp层面（内核层/传输层）

它的keep-alive的作用主要是tcp的连接保活。

比如说，客户端和服务器建立了一条tcp连接，互相都很久没有发消息了，所以，一方就会发一个探测包，试探对方是否还在线，如果不在就断开连接，如果还在就继续保持这条tcp连接。

所以，核心是”确认对方是否还在”。

Http2.0的多路复用

解决了数据传输的顺序问题。

在1.1中我们的请求1发出去，必须等到请求1的返回结果，才能继续发起请求2，这样会造成前面请求阻塞后面的问题，也叫做http层面的对头阻塞。

但是http2.0利用多路复用技术，将数据包拆分的更小，利用帧(frame)和流(stram)可以不需要保证数据返回的顺序，解决了http层面的对头阻塞问题。

Http3.0

对头阻塞虽然http2.0解决了，但是tcp还是有对头阻塞的问题。

核心就在于，tcp它是全双工，可靠传输协议。

所以，HTTP3.0直接将tcp换成了udp传输协议。

彻底解决了，tcp存在的队头阻塞问题。

闭包怎么防止内存泄漏

  1. 当闭包不使用时，主动将引用的闭包函数置为空
  2. 使用弱引用数据结构（weakMap、weakSet）当外部对象无其他强引用时，弱引用允许其被自动回收。
  3. 使用立即执行函数，避免全局作用域污染
  4. 闭包内优先使用局部变量，避免直接引用外部长生命周期变量（如全局变量或 DOM 元素）。
  5. 若闭包绑定为 DOM 事件监听器，在元素销毁前需显式移除监听，防止闭包因元素引用而无法释放。
  6. 若闭包涉及 setInterval 或 setTimeout，需在适当时机调用 clearInterval/clearTimeout 终止计时器。

浏览器内核是什么？

浏览器内核（也称为渲染引擎或排版引擎）是浏览器的核心组件，负责将网页的代码（如 HTML、CSS、JavaScript）转换为用户可视化的页面。它决定了浏览器如何解析、渲染和显示网页内容，直接影响网页的加载速度、兼容性和显示效果。

用户常见问题：

  • 为什么同一网页在不同浏览器显示不同？
    不同内核的解析和渲染规则差异导致。
  • 如何解决兼容性问题？
    开发者需使用 Polyfill 或 CSS 前缀，普通用户可更新浏览器至最新版本。

Polyfill是什么？

Polyfill 是一种用于填补浏览器功能缺失的代码，它可以让旧版本或不支持某些新特性的浏览器“模拟”实现这些功能，从而使开发者能够统一使用最新的 Web 标准（如 HTML5、CSS3、ES6+ 等），而无需担心兼容性问题。

JS为什么会阻塞主线程？

JavaScript 的阻塞行为源于其 执行环境的设计 和 对 DOM/CSSOM 的依赖。

  • js是单线程的，浏览器主线程（负责解析 HTML、执行 JS、处理布局和渲染）同一时间只能执行一个任务。

  • 浏览器把<script>标签的代码当成同步代码了

  • JS 可能修改 DOM 和 CSSOM

    （1）js可以操作dom结构，如果浏览器不暂停解析html，js修改了dom结构的话，就会导致后续解析的html与当前dom状态不一致，引发不可预测的结果；

    （2）js可能依赖后续dom，如果访问后面没有解析的元素。浏览器不知道js会不会访问后续的dom元素，保守处理就先暂停解析，先执行js，确保js运行时的dom状态是确定。

为什么css不会阻塞进程？

1. 并行下载与渐进解析

  • 浏览器遇到 <link rel="stylesheet"> 时，会 异步下载 CSS 文件（不阻塞 HTML 解析）。
  • DOM 解析可以继续：HTML 解析器会继续构建 DOM 树，无需等待 CSS 下载完成。

2. CSSOM 的构建与渲染阻塞

  • 虽然 CSS 不会阻塞 DOM 解析，但它会 阻塞渲染树的生成（即页面实际显示）：
    • 浏览器必须将 DOM 树 和 CSSOM 树 合并为渲染树（Render Tree）后才能绘制页面。
    • 如果 CSS 未加载完成，浏览器会 推迟渲染（保持白屏），但 DOM 解析可能仍在后台进行。

3. CSS 对 JS 执行的间接阻塞

  • 如果 JS 试图访问某些 CSS 属性（如元素尺寸、样式），浏览器可能需要等待 CSSOM 构建完成 才能确保结果正确。
  • 因此，若在 JS 前有未加载完成的 CSS，浏览器会 先暂停 JS 执行，直到 CSS 下载并解析完毕。
行为 JavaScript CSS
阻塞 DOM 解析 直接阻塞（除非用 async/defer） 不阻塞（DOM 解析可继续）
阻塞渲染 间接阻塞（因 DOM 解析暂停） 直接阻塞（渲染树需 CSSOM）
并行下载 可能（但执行仍阻塞） 是（下载不阻塞 DOM 解析）
对主线程的占用 高（同步执行占用主线程） 低（CSSOM 构建在主线程，但可与其他任务交错）

JWT 的优点

  • 无状态：服务端无需存储会话信息，降低数据库压力，适合横向扩展。
  • 跨语言支持：JSON 和标准签名算法，主流编程语言均可实现。
  • 灵活性：Payload 可自定义数据，满足不同业务需求。

JWT 的缺点及解决方案

  1. Token 无法主动失效
    • 问题：JWT 一旦签发，在过期前始终有效，无法强制废除（如用户退出登录）。
    • 解决方案：
      • 设置较短的过期时间（如 15 分钟），结合 Refresh Token 续签。
      • 维护 Token 黑名单（如使用 Redis 记录已注销的 Token）。
  2. Token 可能被窃取
    • 问题：若 Token 泄露，攻击者可冒用身份。
    • 解决方案：
      • 使用 HTTPS 防止中间人攻击。
      • 敏感操作要求二次验证（如密码、短信验证码）。
      • 将 Token 存储在 HttpOnly Cookie 中，防范 XSS 攻击。
  3. Payload 数据膨胀
    • 问题：携带过多数据会增加 Token 长度，影响网络性能。
    • 解决方案：仅存储必要标识（如 userId），其他信息通过标识查询数据库。

定义：

用户只需一次登录认证，即可访问多个相互信任的应用或系统，无需重复输入账号密码。

模式

SESSION + COOKIE 模式

劣势：这个模式很烧钱，项目太大，人很多的话，随着子系统的不断扩大，表格也在不断增大，就很烧钱，成本很高。

TOKEN 模式

劣势：认证中心失去了对用户的控制

TOKEN + REFRESHTOKEN 模式

意为发两个token，token的时间很短可能只有十几二十分钟，但是refresh token 的时间很长，可能有一周或者一个月，当token没过期时可以正常访问子系统，过期了之后可以用refresh token来访问认证中心，然后认证中心返回新token。这样认证中心可以选择发或者不发来实现对用户的控制。

优势：增加对用户的控制力

核心原理

  1. 统一认证中心（Identity Provider, IdP）
    • 所有系统信任同一认证服务（如企业内部的SSO服务器、第三方平台如Google）。
  2. 登录流程：
    • 步骤1：用户首次访问系统A，被重定向到认证中心登录。
    • 步骤2：认证成功后，认证中心颁发令牌（Token）或 票据（Ticket）。
    • 步骤3：用户访问系统B时，系统B向认证中心验证Token有效性，通过后允许访问。

SSO 的优势

  1. 用户体验提升：减少重复登录操作，提高效率。
  2. 密码管理简化：用户只需记住一个账号密码。
  3. 安全管理统一：集中管理权限、审计日志，降低密码泄露风险。

SSO 的挑战与风险

  1. 单点故障：认证中心宕机会导致所有系统不可用。
    • 解决方案：集群部署、负载均衡、故障转移。
  2. 安全风险集中：攻击者攻破认证中心可访问所有系统。
    • 解决方案：强化认证中心安全（多因素认证、入侵检测）。
  3. 跨域问题：不同域名或组织的系统需解决Cookie共享和信任链问题。
    • 解决方案：使用OAuth2.0的跨域Token传递或SAML断言。

SSO 工作流程示例（以OAuth2.0为例）

  1. 用户访问App A：
    • App A 重定向用户到认证中心（如Google登录页）。
  2. 用户登录认证中心：
    • 输入账号密码，完成认证。
  3. 颁发授权码（Authorization Code）：
    • 认证中心返回授权码至App A。
  4. App A换取访问令牌（Access Token）：
    • 向认证中心发送授权码，换取Token。
  5. 访问其他关联服务（App B）：
    • App A携带Token访问App B，App B向认证中心验证Token有效性后放行。

SSO 应用场景

  1. 企业内部系统集成：
    • 员工一次登录后访问OA、CRM、ERP等系统。
  2. 跨平台服务：
    • 使用Google账号登录Spotify、Zoom等第三方应用。
  3. 云服务生态：
    • AWS、Azure云平台内多服务的无缝切换。

SSO 与传统登录对比

对比项 传统登录 SSO
登录次数 每个系统独立登录 一次登录，全网通行
密码管理 多套密码，易遗忘或重复使用 单一密码，集中管理
安全性 分散风险，但弱密码易被各个击破 集中风险，但可强制强密码策略和多因素认证
运维成本 分散维护，成本高 统一维护，成本低

SSO 安全实践

  1. 强制HTTPS：防止Token在传输中被窃取。
  2. 短期Token有效期：Access Token设置较短有效期（如1小时），通过Refresh Token续签。
  3. 多因素认证（MFA）：敏感操作要求短信验证码、生物识别等二次验证。
  4. Token绑定设备/IP：限制Token只能在特定设备或网络环境下使用。

vite为什么要使用esbuild和rollup两个？

为什么不统一用一个工具？

（1）esbuild 的局限性

  • 功能覆盖不足：
    • 生产级 CSS 代码分割、资源处理等能力较弱。
    • 插件系统不够成熟（esbuild 插件生态远不如 Rollup）。
  • 稳定性问题：esbuild 的某些优化策略可能过于激进，导致边缘场景问题。

（2）Rollup 的不足

  • 开发阶段速度慢：Rollup 的实时编译速度无法满足开发环境对即时反馈的需求。

Vite 的分工设计

  • 开发阶段：
    • 用 esbuild 快速处理依赖预构建和源码转换，优先保障开发速度。
  • 生产阶段：
    • 用 Rollup 进行精细化打包，确保代码质量、兼容性和扩展性。

对比

场景 esbuild Rollup
开发环境 极速启动、实时编译、按需加载 不适用（速度慢）
生产环境 不适用（功能有限） 精细化 Tree Shaking、代码分割
核心优势 速度极快 生态丰富、输出稳定
适用阶段 依赖预构建、开发服务器 生产打包

总结

Vite 选择 “开发用 esbuild，生产用 Rollup” 的核心逻辑是：

  1. 开发环境追求速度：用 esbuild 的极致性能缩短等待时间。
  2. 生产环境追求质量：用 Rollup 的成熟生态保障代码优化和稳定性。

这种分工既发挥了现代工具的性能潜力，又规避了单一工具的局限性，是工程实践中的典型权衡策略。

4. 特性对比

特性 CommonJS ES Module
Tree Shaking 不支持（动态加载导致无法静态分析） 支持（静态结构便于打包工具优化）
循环依赖 支持但可能导致逻辑混乱 支持且更安全（静态引用解决）
顶层 this 指向 this 指向当前模块的 exports 对象 this 指向 undefined（严格模式）
代码执行时机 模块加载时立即执行 模块预解析后延迟执行（按需）

5. 典型使用场景

  • CommonJS：
    • Node.js 服务端开发（历史原因）。
    • 旧项目或需要动态加载模块的场景。
  • ES Module：
    • 现代前端工程（Vue/React 项目）。
    • 需要 Tree Shaking 优化代码体积的场景。
    • 浏览器原生支持的模块化方案。

7. 如何迁移或兼容？

  • Node.js 中同时支持两种规范：
    • 使用 .cjs 扩展名表示 CommonJS 模块。
    • 使用 .mjs 扩展名或 package.json 中设置 "type": "module" 启用 ESM。
  • 工具链支持：
    • 使用 Babel 或 TypeScript 将 ESM 转换为 CommonJS（兼容旧环境）。
    • 使用 Webpack/Rollup 等打包工具统一处理模块化差异。

总结

核心差异 CommonJS ES Module
设计目标 服务端（Node.js） 浏览器 + 现代 JS 生态
加载方式 同步、动态 静态、支持异步
导出值类型 值的拷贝 值的引用
静态分析 困难（无法 Tree Shaking） 容易（天然支持优化）
未来趋势 逐渐被 ESM 替代（Node.js 已支持） 现代开发的首选标准

选择建议：

  • 新项目优先使用 ES Module（尤其是前端工程）。
  • 维护旧 Node.js 项目时沿用 CommonJS，逐步迁移。

Service worker是什么

Service Worker 是浏览器在后台独立运行的一种 JavaScript 脚本，它的核心作用是增强 Web 应用的能力，使其具备类似原生应用的功能（如离线访问、后台同步、消息推送等）。它是现代 Web 技术（尤其是 PWA，渐进式 Web 应用）的核心组成部分。

核心特性

  1. 离线缓存
    • 可以拦截网络请求，优先从缓存中返回资源，即使没有网络也能加载页面。
    • 通过 Cache API 管理缓存策略（例如预缓存关键资源）。
  2. 网络代理
    • 通过 fetch 事件拦截和处理所有 HTTP 请求，可动态决定返回缓存内容还是重新请求。
  3. 后台运行
    • 即使页面关闭或浏览器未激活，Service Worker 仍可在后台执行任务（如数据同步、接收推送通知）。
  4. 生命周期管理
    • 生命周期包括注册（register）、安装（install）、激活（activate）等阶段。
    • 需通过代码控制更新逻辑，避免旧版本缓存问题。

使用场景

  • 离线优先应用
    例如文档工具、新闻阅读器，用户断网时仍可访问已缓存内容。
  • 性能优化
    预缓存静态资源（CSS、JS、图片），减少重复请求。
  • 后台同步
    在网络恢复后自动同步用户操作（如提交表单失败后重试）。
  • 推送通知
    向用户发送实时通知（即使浏览器未打开）。

  1. HTTPS 要求

  2. 作用域限制
    • 只能控制其所在目录及子目录的请求（例如 /sw.js 默认作用域为根目录）。
  3. 单例模式
    • 每个作用域只能有一个激活的 Service Worker。
  4. 无法直接操作 DOM
    • 需通过 postMessage 与主线程通信。

微前端是什么

核心：大拆小，拆小的每一个组件都能做到独立的自治。

微前端（Micro Frontends）是一种将前端应用拆分为独立、可独立开发和部署的小型应用的架构模式，其核心思想借鉴了后端的微服务（Microservices）理念。通过微前端，不同团队可以独立负责不同功能模块，使用不同的技术栈，最终将这些模块整合成一个完整的应用。

核心思想

  1. 模块化拆分
    将大型前端应用拆分为多个独立的功能模块（如导航、购物车、用户中心等），每个模块称为一个“微前端”。
  2. 自治团队
    每个模块由独立团队负责开发、测试和部署，减少团队间的耦合和协调成本。
  3. 技术无关性
    不同模块可以使用不同的技术栈（如 React、Vue、Angular），甚至不同的构建工具。
  4. 渐进式升级
    允许逐步替换老旧代码或技术栈，无需一次性重构整个应用。

典型应用场景

  • 复杂企业级应用：如电商平台、后台管理系统，多个功能模块需要并行开发。
  • 多团队协作：不同团队负责不同功能，避免技术栈强绑定。
  • 遗留系统现代化：逐步替换旧系统的某些部分，而非全盘重写。
  • 多技术栈共存：例如主应用用 React，子模块用 Vue 或原生 JavaScript。

常见技术实现方案

  1. 基于 iframe 的嵌套
    • 优点：天然隔离，技术无关。
    • 缺点：通信复杂（需通过 postMessage），加载性能差，SEO 不友好。
  2. Web Components
    • 利用自定义元素（Custom Elements）和 Shadow DOM 实现组件隔离。
    • 示例：将子模块封装为 Web Component，主应用动态加载。
  3. 模块联邦（Module Federation）
    • 通过 Webpack 5 的 Module Federation 功能，动态加载远程模块。
    • 示例：主应用加载其他团队构建的 React/Vue 组件。
  4. 基座模式（Single-SPA 等框架）
    • 主应用作为“基座”，通过路由动态加载子应用。
    • 子应用需遵循生命周期钩子（如 bootstrap, mount, unmount）。

优势

  • 独立开发与部署：团队可独立迭代，减少发布风险。
  • 技术多样性：允许混合使用不同框架或技术。
  • 增量升级：逐步替换旧代码，降低重构风险。
  • 可维护性：模块边界清晰，复杂度可控。

挑战

  • 依赖管理：共享依赖（如 React、Vue）可能导致版本冲突。
  • 通信机制：跨模块状态共享（如用户登录态）需要设计通信方案（如 Custom Events、Redux）。
  • 性能问题：子应用加载可能影响首屏速度，需优化资源加载策略。
  • 标准化难度：不同团队的技术选型差异可能导致维护成本上升。

总结

微前端适合复杂的前端项目，尤其是需要多团队协作、技术栈多样化或渐进式升级的场景。但它并非银弹，需根据项目需求权衡利弊。常见的实践框架包括 Single-SPA、qiankun（阿里开源）、Webpack Module Federation 等。

Mixin是什么

在前端开发中，Mixin（混入） 是一种代码复用模式，主要用于将可复用的功能逻辑、样式或组件行为“混合”到多个地方，从而减少重复代码并提高可维护性。它在不同技术栈中有不同的实现方式，以下是典型应用场景：

一、在 CSS 预处理器（如 Sass/Less） 中：

Mixin 用于复用样式代码块，支持参数化，类似函数。

二、在 JavaScript 或前端框架（如 Vue） 中：

Mixin 用于复用组件逻辑（数据、方法、生命周期钩子等）。
示例：Vue 中复用“用户登录状态”逻辑

作用：跨组件共享通用逻辑（如日志、权限、埋点）。

四、核心优势：

  1. 减少重复代码：将通用逻辑集中管理。
  2. 解耦功能：将功能模块化，便于维护。
  3. 灵活组合：按需混合多个功能到目标组件/样式。

五、注意事项：

  • 滥用风险：过度使用会导致代码关系复杂，建议优先考虑组合式 API（如 Vue 3 的 Composition API）。
  • 框架差异：不同技术栈的实现方式不同（如 Sass Mixin vs. Vue Mixin）。

总结：Mixin 是前端中实现代码复用的重要模式，合理使用能显著提升开发效率，但需注意适用场景和潜在问题。

$set()是干什么的

在 Vue.js 中，$set（或 Vue.set）是用于确保数据变更能够触发视图更新的响应式方法，尤其在处理动态添加对象属性或修改数组元素时非常关键。以下是它的核心作用、适用场景和具体用法：

一、$set 的作用

Vue 的响应式系统无法自动检测以下两种数据变更：

  1. 直接通过索引修改数组元素（如 arr[0] = newValue）。
  2. 向对象动态添加新属性（如 obj.newKey = value）。

$set 的作用是绕过这一限制，强制让 Vue 感知到数据变化并更新视图。
