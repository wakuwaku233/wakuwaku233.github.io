vue与react的区别

相似之处：

  • 都将注意力集中保持在核心库，而将其他功能如路由和全局状态管理交给相关的库；
  • 都有自己的构建工具，能让你得到一个根据最佳实践设置的项目模板；
  • 都使用了Virtual DOM（虚拟DOM）提高重绘性能；
  • 都有props的概念，允许组件间的数据传递；
  • 都鼓励组件化应用，将应用分拆成一个个功能明确的模块，提高复用性。

不同之处 ：

1）数据流

Vue默认支持数据双向绑定，而React一直提倡单向数据流

2）虚拟DOM

Vue2.x开始引入”Virtual DOM”，消除了和React在这方面的差异，但是在具体的细节还是有各自的特点。

  • Vue宣称可以更快地计算出Virtual DOM的差异，这是由于它在渲染过程中，会跟踪每一个组件的依赖关系，不需要重新渲染整个组件树。
  • 对于React而言，每当应用的状态被改变时，全部子组件都会重新渲染。当然，这可以通过 PureComponent / shouldComponentUpdate这个生命周期方法来进行控制，但Vue将此视为默认的优化。

3）组件化

React与Vue最大的不同是模板的编写。

  • Vue鼓励写近似常规HTML的模板。写起来很接近标准 HTML元素，只是多了一些属性。
  • React推荐你所有的模板通用JavaScript的语法扩展——JSX书写。

具体来讲：React中render函数是支持闭包特性的，所以import的组件在render中可以直接调用。但是在Vue中，由于模板中使用的数据都必须挂在 this 上进行一次中转，所以 import 一个组件完了之后，还需要在 components 中再声明下。

4）监听数据变化的实现原理不同

  • Vue 通过 getter/setter 以及一些函数的劫持，能精确知道数据变化，不需要特别的优化就能达到很好的性能
  • React 默认是通过比较引用的方式进行的，如果不优化（PureComponent/shouldComponentUpdate）可能导致大量不必要的vDOM的重新渲染。这是因为 Vue 使用的是可变数据，而React更强调数据的不可变。

5）高阶组件

react可以通过高阶组件（HOC）来扩展，而Vue需要通过mixins来扩展。

高阶组件就是高阶函数，而React的组件本身就是纯粹的函数，所以高阶函数对React来说易如反掌。相反Vue.js使用HTML模板创建视图组件，这时模板无法有效的编译，因此Vue不能采用HOC来实现。

6）构建工具

两者都有自己的构建工具：

  • React ==> Create React APP
  • Vue ==> vue-cli

7）跨平台

  • React ==> React Native
  • Vue ==> Weex

Vue的优点

  • 轻量级框架：只关注视图层，是一个构建数据的视图集合，大小只有几十 kb ；
  • 简单易学：国人开发，中文文档，不存在语言障碍 ，易于理解和学习；
  • 双向数据绑定：保留了 angular 的特点，在数据操作方面更为简单；
  • 组件化：保留了 react 的优点，实现了 html 的封装和重用，在构建单页面应用方面有着独特的优势；
  • 视图，数据，结构分离：使数据的更改更为简单，不需要进行逻辑代码的修改，只需要操作数据就能完成相关操作；
  • 虚拟DOM：dom 操作是非常耗费性能的，不再使用原生的 dom 操作节点，极大解放 dom 操作，但具体操作的还是 dom 不过是换了另一种方式；
  • 运行速度更快：相比较于 react 而言，同样是操作虚拟 dom，就性能而言， vue 存在很大的优势。

浏览器缓存

http里的缓存，本质上只是浏览器和业务侧，根据不同的报文字段，做出不同的缓存动作而已。

强缓存（本地缓存）

浏览器本地在有效时间内强制缓存

弱缓存（协商缓存）

和服务器沟通，由服务器告知浏览器是否使用缓存

四种缓存协议如下：

Cache-Control

通过响应头设置Cache-Control和max-age，指定该请求需要在浏览器缓存多久，在设置的时间内重复请求，则无需再次访问服务器。

以下是假如说设置10s：

十秒内访问，就会直接在前端访问disk cache，十秒之后再去申请新的数据。

Expires

通过响应头设置Expires，指定该请求需要在浏览器缓存多久，在设置的时间内重复请求，则无需再次访问服务器，直接从浏览器拿到数据。

ETag / If-None-Match （协商缓存 ）

ETag（唯一资源标识）需要搭配 If-None-Match 使用，在首次请求时，服务端会把结果签名缓存在服务端，并设置在响应头ETag字段中，返回给浏览器。业务册则需要缓存ETag和结果数据，并且在下次请求的时候，带在请求头 If-none-match 字段中，服务端再次接收到请求后，判断ETag和 If-none-match 是否相等，如果相等，意味着数据结果并没有发生变化，直接返回304，业务侧接收到304后，直接访问之前的缓存结果数据。

Last-Modified / If-Modified-Since

这俩需要搭配使用，在首次请求资源时，服务端在响应头中设置last-modified字段，返回给浏览器，右侧则需要缓存last-modified和结果数据，并且在下一次请求的时候带上请求头if-modified-since，服务端再次接收到请求后，判断 if-modified-since 是否大于等于 last-modified，如果是，则意味着结果数据并没有发生变化，直接返回304，浏览器接受到304后直接访问浏览器缓存的数据。

如何取消缓存

前端无法直接设置服务器的缓存头，但可以通过以下方式间接影响缓存：

  • 请求头（Request Headers）
    在发起请求时，前端可以添加头来要求特定缓存行为：

    • Cache-Control: no-cache：强制向服务器验证缓存是否有效。
    • If-None-Match（携带服务器返回的 ETag）：触发 304 响应。
    • If-Modified-Since（携带服务器返回的 Last-Modified）：触发 304 响应。

requestIdleCallBack

requestIdleCallback 是浏览器提供的一种优化机制，允许开发者在浏览器空闲时段（Idle Period）执行低优先级的后台任务，避免阻塞关键的用户交互和渲染操作。它是实现高性能 Web 应用的重要工具，尤其在处理非紧急任务（如日志上报、数据预加载等）时非常有用。

核心原理

  1. 事件循环中的空闲期
    浏览器主线程的事件循环（Event Loop）在处理完每一帧的渲染、用户输入、定时器等任务后，可能存在空闲时间。requestIdleCallback 利用这些空闲时段执行任务，避免抢占高优先级资源。
  2. 回调执行时机
    • 当浏览器判断当前没有更高优先级的任务需要处理时，触发回调。
    • 如果回调未在指定时间内执行（通过 timeout 参数设置），浏览器会强制在下一帧执行。
  3. 避免阻塞
    回调函数应尽量短小（通常不超过 50ms），否则浏览器可能中断执行，导致任务未完成。

基本用法

应用场景

场景 说明
数据上报（Analytics） 将用户行为日志暂存，在空闲时批量发送，减少对主线程的干扰。
预加载非关键资源 提前加载后续页面可能需要的图片、数据，但不在首屏关键路径上。
延迟计算（如统计、排序） 对非实时性要求高的数据进行处理（如用户离开页面后的计算）。
渐进式渲染 分块渲染大型列表或复杂组件，避免一次性渲染导致的卡顿。

注意事项

  1. 避免在回调中修改 DOM
    修改 DOM 可能触发重排/重绘，破坏空闲期的优化目标。若必须操作 DOM，优先使用 requestAnimationFrame。

  2. 超时（timeout）需谨慎使用
    设置 timeout 会强制浏览器在指定时间内执行回调，但可能打断用户的关键操作。仅在必要时使用。

Web Worker 无法直接修改 DOM。这是由浏览器的线程模型和安全机制决定的，但可以通过间接通信的方式实现 DOM 更新。以下是详细解释和解决方案：

为什么 Web Worker 不能直接操作 DOM？

  1. 线程安全限制
    DOM 操作必须在浏览器主线程（UI 线程）中进行，而 Web Worker 运行在独立的后台线程中。如果允许 Worker 直接操作 DOM，可能导致多线程竞争资源，引发渲染不一致或崩溃。
  2. Worker 环境隔离
    Web Worker 没有访问 window、document 等全局对象的权限，其作用域仅限于 DedicatedWorkerGlobalScope（或 SharedWorkerGlobalScope）。

如何间接实现 DOM 修改？

虽然 Worker 无法直接操作 DOM，但可以通过消息传递（postMessage）与主线程通信，由主线程完成 DOM 更新。

  2. 缓冲区扩展（扩展1-2屏的缓冲区）

  3. css渲染优化（启用硬件加速）

    • 重构后：提取公共组件/函数，重复代码降至 480 行（占 8%）。
    • 复用率提升：(1200 - 480)/6000 * 100% = **12%**。

2. 组件/函数复用次数统计

  • 方法：统计公共组件或工具函数在项目中的引用次数。
  • 指标：
    • 组件复用率 = 公共组件使用次数 / 总组件数
    • 函数复用率 = 公共函数调用次数 / 总函数调用数
  • 示例：
    • 封装上传组件后，在 15 个页面中被引用，占全部文件上传场景的 75%。
    • 复用率提升：从 0%（无复用）到 75%。

3. 代码行数对比（DRY 原则）

  • 计算方式：对比重构前后的代码行数减少量。
  • 示例：
    • 封装表单校验工具前：每个页面有 50 行校验代码，10 个页面共 500 行。
    • 封装后：工具函数 100 行 + 各页面引用 10 行 → 总 100 + 10*10 = 200 行。
    • 减少行数：500 - 200 = 300 行（复用率提升 60%）。

4. 构建产物体积优化

  • 指标：通过打包工具（Webpack/Vite）分析构建产物体积变化。

  • 案例：

    • 提取公共工具库前：总 JS 体积 2MB，其中重复代码占 400KB。
    • 提取后：公共库 200KB + 主包 1.4MB → 总 1.6MB。
    • 体积减少率：(2 - 1.6)/2 * 100% = **20%**。

5. 维护成本降低（开发效率）

  • 定性指标：
    • 需求迭代速度：相同功能开发时间减少（如复用组件后，开发时间从 2 天降至 0.5 天）。
    • Bug 修复范围：公共组件修复 1 次 vs 多个页面修复 N 次。

数据计算依据：
在「融资通」项目中，我们通过以下方式量化 12% 的代码复用率提升：

  1. 静态分析：使用 SonarQube 检测到重构前重复代码占比 18%，提取 6 个公共组件和 10 个工具函数后，重复率降至 6%，提升 (18% - 6%) = 12%。
  2. 体积优化：构建产物体积从 3.2MB 降至 2.8MB，减少 12.5%（其中 60% 的缩减来自代码复用）。
  3. 维护成本：公共表单校验组件在 8 个页面复用，相同需求开发时间减少 40%。

其他量化指标：

  • 组件复用次数：地图标点组件被 5 个模块引用，减少 200 行重复代码。
  • 打包体积：通过 Tree Shaking 移除未使用代码，主包体积减少 15%。

关于登录模块

1. 登录模块实现流程

  • 用户提交凭证：前端将用户输入的用户名和密码通过HTTPS加密传输到后端。
  • 验证用户信息：
    • 后端查询数据库，验证用户名和密码（密码存储为哈希加盐的形式）。
    • 验证通过后，生成JWT（JSON Web Token）作为身份凭证。
  • 生成Token：
    • JWT结构：Header（算法）、Payload（用户ID、角色、过期时间等）、Signature（签名）。
    • 使用密钥对Header和Payload签名，确保Token不可篡改。
  • 返回Token：后端将Token返回给前端，通常通过响应体或Set-Cookie头部。
  • 前端存储Token：前端将Token保存在localStorage、sessionStorage或HttpOnly Cookie中。
  • 后续请求携带Token：前端在请求头（如Authorization: Bearer <token>）中附加Token，供后端鉴权。

2. Token能否携带用户信息？

  • 可以，但需谨慎：
    • JWT的Payload部分可自定义存储用户ID、角色等非敏感信息（如userId、role）。
    • 避免存储密码、邮箱等敏感数据，因为Payload仅经过Base64编码，可被客户端解码。
    • 优点：后端无需频繁查库，直接从Token中解析用户信息，提升性能。

3. Token存储位置

  • 客户端存储：
    • localStorage/sessionStorage：易于实现，但需防范XSS攻击（如避免动态插入未转义内容）。
    • HttpOnly Cookie：更安全（无法通过JS读取），但需处理CSRF防护（如SameSite属性、Anti-CSRF Token）。
  • 服务端存储：
    • 若为无状态JWT，服务端不存储Token，仅通过签名验证有效性。
    • 若需实现Token注销/黑名单，需结合Redis等缓存，存储已失效的Token直至过期。

4. 总结：

  • 技术选型：
    • 选择JWT因其无状态特性，适合分布式系统，减少服务端会话存储压力。
  • 安全性措施：
    • 传输安全：全程HTTPS，防止中间人攻击。
    • Token有效期：设置较短的过期时间（如15分钟），结合Refresh Token延长会话。
    • 防御XSS/CSRF：对前端输入做转义、CSP策略；Cookie设置SameSite=Strict、Secure。
  • Token刷新机制：
    • 使用长时效的Refresh Token（存储于HttpOnly Cookie）换取新的Access Token，平衡安全性与用户体验。
  • 敏感信息处理：
    • Token中仅包含必要标识（如用户ID），敏感权限需二次验证或实时查询数据库。

关于事件循环的解答

单线程是异步的原因，事件循环是异步的解决方式。

首先js是单线程的，同步代码给js引擎执行，异步代码交给宿主环境（node/浏览器），他只能一个个的执行同步代码，但是遇到像定时器、ajax、promise这些耗时东西就会阻塞线程，所以就弄出来了任务队列，以前是叫的宏任务和微任务，现在分为很多个队列，微队列、交互队列、延迟队列。各个事件放到对应的队列中去。当同步代码一执行完，他就会反复的查看任务队列，看有没有异步的任务需要执行，然后就放到任务队列里面去执行，然后周而复始的进行这个操作。这个过程就叫做事件循环。
